# Loading an FPGA bitstream from the PS (Linux) side

On Zynq UltraScale+ the PL fabric can be (re)configured at run time from the
running PS through the **PCAP** (Processor Configuration Access Port), driven by
the Linux **FPGA manager** subsystem. No JTAG, no rebuilt `BOOT.BIN`, no reboot.

This template ships the board ready for it:

- the kernel is built with `CONFIG_FPGA_MGR_ZYNQMP_FPGA`, `CONFIG_FPGA_REGION`,
  `CONFIG_OF_FPGA_REGION`, `CONFIG_OF_OVERLAY` and `CONFIG_CONFIGFS_FS`
  (see `linux/config/rk-xczu15eg-f.cfg`);
- the device tree is compiled with `dtc -@`, keeping `__symbols__` so overlays
  can resolve `&fpga_full`;
- a helper, **`/usr/local/bin/load-bitstream.sh`**, is in the rootfs;
- `BOOT.BIN` carries **no** bitstream, so the PL is yours to program.

## 1. The big picture

```
  Vivado  ──►  my_design.bit ──[ bootgen ]──►  my_design.bit.bin  (raw, no header)
                                                    │  scp to board
                                                    ▼
   /lib/firmware/my_design.bit.bin
                                                    │  load-bitstream.sh
                                                    ▼
   device-tree overlay on &fpga_full  ──►  fpga-region  ──►  zynqmp-fpga (PCAP)
                                                    │
                                                    ▼
                            PL fabric configured, state = "operating"
```

## 2. Prepare the bitstream (build host)

The FPGA manager wants a **raw** bitstream (`.bit.bin`), i.e. the Vivado `.bit`
with its ASCII header stripped and byte order fixed. Use the helper:

```bash
scripts/bit2bin.sh my_design.bit          # -> my_design.bit.bin (next to the .bit)
```

Internally that runs `bootgen … -process_bitstream bin` on a one-line BIF:

```
all:
{
    [destination_device=pl] my_design.bit
}
```

> A plain `.bit` often also works (the `zynqmp-fpga` driver tolerates the
> header), but `.bit.bin` is the canonical, reliable form — always convert.

Copy it to the board:

```bash
scp my_design.bit.bin riguke@<board-ip>:/tmp/
```

## 3. Program the PL (on the board)

```bash
sudo load-bitstream.sh /tmp/my_design.bit.bin
sudo load-bitstream.sh --status
```

Expected:

```
load-bitstream: installed firmware /lib/firmware/my_design.bit.bin
load-bitstream: programmed via device-tree overlay (&fpga_full)
load-bitstream: fpga state: operating
```

### What the helper does

1. Copies the bitstream into `/lib/firmware/` (where the kernel firmware loader
   looks).
2. Generates a tiny device-tree overlay and applies it through configfs:

   ```dts
   /dts-v1/;
   /plugin/;
   &fpga_full {
       firmware-name = "my_design.bit.bin";
   };
   ```
   ```bash
   dtc -@ -I dts -O dtb -o ovl.dtbo ovl.dts
   mkdir /sys/kernel/config/device-tree/overlays/rk-fpga-full
   cat ovl.dtbo > /sys/kernel/config/device-tree/overlays/rk-fpga-full/dtbo
   ```
   Applying the overlay makes the `fpga-region` driver hand the firmware to the
   `zynqmp-fpga` manager, which streams it over PCAP.
3. Falls back to the legacy Xilinx sysfs interface
   (`/sys/class/fpga_manager/fpga0/{flags,firmware}`) if overlays are
   unavailable.

To **unload** (remove the region/overlay):

```bash
sudo rmdir /sys/kernel/config/device-tree/overlays/rk-fpga-full
```

## 4. Doing it by hand (no helper)

Full bitstream, the manual equivalent of the helper:

```bash
cp my_design.bit.bin /lib/firmware/
cat > ovl.dts <<'EOF'
/dts-v1/; /plugin/;
&fpga_full { firmware-name = "my_design.bit.bin"; };
EOF
dtc -@ -I dts -O dtb -o ovl.dtbo ovl.dts
mkdir -p /sys/kernel/config/device-tree/overlays/full
cat ovl.dtbo > /sys/kernel/config/device-tree/overlays/full/dtbo
cat /sys/class/fpga_manager/fpga0/state          # -> operating
```

## 5. Adding the PL devices to Linux

A bare full-reconfiguration overlay just programs the fabric. If your design
exposes AXI peripherals (AXI-GPIO, BRAM, a custom IP…), put their device nodes
**inside the same overlay** so Linux probes drivers for them once the bitstream
is live:

```dts
/dts-v1/; /plugin/;
&fpga_full {
    firmware-name = "my_design.bit.bin";
    #address-cells = <2>;
    #size-cells = <2>;

    gpio@80000000 {
        compatible = "xlnx,axi-gpio-2.0", "xlnx,xps-gpio-1.00.a";
        reg = <0x0 0x80000000 0x0 0x10000>;
        xlnx,all-outputs = <1>;
        xlnx,gpio-width = <4>;
        #gpio-cells = <2>;
        gpio-controller;
    };
};
```

See `examples/pl-blinky-overlay/` for a complete, ready-to-build example.

## 6. Partial reconfiguration

For a partial bitstream (a reconfigurable partition), pass `--partial`:

```bash
sudo load-bitstream.sh my_partial.bit.bin --partial
```

This sets the partial-reconfig flags on the FPGA manager. Partial bitstreams must
be generated by the Vivado DFP/PR flow against a static design that defines the
reconfigurable partition; that is a project-specific design step beyond this
template.

## 7. Requirements & troubleshooting

| symptom | cause / fix |
|---------|-------------|
| `no /sys/class/fpga_manager/fpga0` | kernel lacks `FPGA_MGR_ZYNQMP_FPGA`; this template enables it — check you booted the template's `Image`. |
| overlay apply fails, label `fpga_full` not found | the running `system.dtb` was built **without** `-@`; regenerate with `board/device-tree/gen_devicetree.sh` (it uses `dtc -@`). |
| `state` stays `unknown`/not `operating` | wrong/over-large bitstream, or it was not converted to raw `.bit.bin`. Re-run `scripts/bit2bin.sh`. |
| works once, second load fails | remove the previous overlay first (`rmdir …/overlays/<name>`). |
| AXI IP present but no `/dev` node | add the IP's DT node to the overlay (section 5). |

## 8. Why not put the bitstream in BOOT.BIN?

You can (`make boot BITSTREAM=my_design.bit`) and the FSBL will configure the PL
before Linux. But keeping it out is what makes this a flexible platform: one
golden boot image, many interchangeable PL designs loaded and swapped from
userspace — ideal for development, field updates, and acceleration workloads.
